## What a stolen API token can and cannot do

An API token is a password for a script, so treat it like one: keep it in an environment variable or a secret store, never in a repository. Anyone holding it can do what its scope allows for as long as it lives (at most 365 days, 90 by default) and until the account's role is lowered or it is revoked.

- **It can** read what its account's role may read (`read`), make the day-to-day writes the role allows (`operate`) and, for an admin account's `admin` token, register or delete machines, change alert rules and maintenance windows, read the audit log and the webhook list (a `read` token cannot, because the audit trail and the outbound addresses are administration) and delete or test a webhook.
- **It cannot** change the password, email, phone number, two-step settings, sessions or provider links, make or revoke a token, invite anyone, add or change a webhook, upload firmware, rotate a machine's key, use the admin controls over users, delete the account, export the account's data or open the live socket. Those need a signed-in session and, for the dangerous ones, a fresh proof, which a token cannot give. A stolen token therefore cannot lock the owner out or make itself permanent.
- **How to revoke.** Delete it with `DELETE /auth/tokens/{id}` (the profile page lists the tokens). Changing the password, turning two-step on or off or signing out the other sessions revokes every token at once. An admin deactivating the account or clearing its sessions does the same and lowering a role lowers every token on the next call.
- **How to tell it was used.** Every audit row a token writes names it (`[via token <id>]`) and the token's last-used time is on the list.
- **Limits of the design.** A token has no address restriction. A token with `operate` or `admin` scope is as powerful as that part of the account, so make the lowest scope that does the job and a short expiry. Only a keyed hash of the secret is stored, so a copy of the database does not give the tokens.

## Known limits

- **There is still no self-service way back for a person who forgets their password.** An admin can email the account a one-time reset link (`POST /auth/users/{id}/reset-link`) and the person chooses a new password with it. A self-service reset (a person asks for their own link) is not built. A person with no admin to ask is helped through the database as before: set a temporary password, bump `token_version` and ask them to change it.
- **The email change notice has a gap by design.** It is not sent to an address typed in less than an hour ago. If an attacker with a password changes the email twice within the hour, the second old address is the attacker's own and is not mailed and only the first notice (to the real owner) goes out.
- **A new email address is not confirmed by a link before the change takes effect.** It was weighed and left out: the confirmation email needs Resend to be configured and an unconfigured deployment (development or a first deploy) could then never change an address. The protections instead are the password (and a two-step code) to change it, every other session ended at once and a notice to the old address.
- **Machine API keys are stored as a keyed hash (migration 031).** The old limit below is closed: `devices.key_hash` is HMAC-SHA256 of the key under a sub-key derived from `SECRET_KEY` for this one purpose, a machine is found by the first 8 characters (`key_id`, in clear) and the hash is compared in constant time. The hash key comes from `services/keys.py` (purpose `device_key`), so when `SECRET_KEY` is rotated a hash made under `SECRET_KEY_PREVIOUS` still verifies and the machine is re-hashed under the new key on its next post. Drop the previous key only after every machine has posted once more or an admin must rotate the key of any that has not. A fast keyed hash is enough because a key is 256 random bits, so guessing cannot be made harder by a slow hash and every ingest post would pay for it. An unknown and a wrong key cost the same and answer the same. A key can be seen only in the reply that makes or rotates it. Rotation is for admins and the machine's owner. A post is refused unless its `(boot, seq)` is newer than the last accepted for a machine that has ever sent the pair (see `POST /telemetry`). That stops a replayed capture. It does not stop someone who holds the key and posts newer pairs, which is what TLS and rotation are for. A fault claim stops a sensor only while an alert says so, every sensor field has a physical range and a daily alert cap is shared out per machine.
- **Two-step secrets are encrypted but the key is on the same server.** A backup alone no longer gives a second factor, but whoever holds both the backup and `SECRET_KEY` can decrypt them. Keep backups off the server and the key out of them.
- **Webhook delivery trusts the address check as it runs.** The address is resolved, checked and connected to as one step, but the check has no memory between sends. A host that is public today and private tomorrow is caught at the next send, not before.
- **Audit entries stay after an account is deleted.** They hold the account's id as text and are returned in the export, but they are not erased with the account.
- **A stranger with many addresses can still guess at one try every 10 seconds on a non-admin account** once it is being guessed at from many places (about 8,600 a day) and at five tries per source for an admin account. The owner is emailed once a day, a good password survives that and two-step stops it. Admin accounts are never slowed by strangers account-wide, so they rely on two-step sign-in, which admins should switch on. A source shared with an attacker (an office address or a /64) is delayed with the attacker.
- **Recovery codes do not exist.** A lost authenticator is handled by an admin clearing two-step. Nothing is stored to hash.
- **An email address that already has an account is revealed to a signed-in person changing their email** (after their proof) and to an admin inviting it. Both need a signed-in account.
- **`ticket_number` is one counter for every ticket.** A person who raises two tickets learns how many others were raised in between.
- **The refresh grace is 10 seconds.** A copy of a refresh token used inside 10 seconds of its rotation is forgiven, so a thief who acts at that moment is not caught by reuse detection. The 15 minute access token and the absolute session end still bound it.
- **The Nginx error log can print a socket's request line.** `access_log off` does not cover it. The first-message form keeps the token out of every address.

## Server limits

- **A backup says who can read it, not who wrote it.** The public key is on the server and anyone who holds it can make a file that `restore.sh` accepts. The off-server copy's object lock is what vouches for a file. Backups are not signed.
- **The API's database role can change its own saved settings between deploys.** PostgreSQL lets a role run `ALTER ROLE ... SET` on itself. `db-role.sh` resets them on every deploy and the check fails if one is present, but between two deploys a code execution in the API could set a `search_path` that stops the API starting. It cannot do more than that.
- **The verification of a release is only as good as the keys in the signer file** and the machine that holds a release key. A stolen release key signs a tag that every line accepts.
- **A body that trickles in one byte at a time holds an Nginx connection for as long as the sender wants,** up to 100 an address. Nginx has no limit on the total time of a body. The body is held in Nginx and never reaches the API until it is whole.

## Notes

**Live socket token:** a browser WebSocket cannot send an `Authorization` header, so the access token travels in the first frame after the connection opens (`{"type":"auth","token":"..."}`, see `frontend/lib/wsUrl.ts`) and never in the address. The protections are that the token is an access token that lasts 15 minutes, that the socket closes when it expires and that the frame must arrive within 5 seconds. The older `?token=` form is allowed only in development (`WS_TOKEN_IN_URL`), so a production API refuses it once set up as documented. A reverse proxy writes its own access log, so keep query strings out of it all the same.

**Where the access token lives:** the access token is in `localStorage` (for the axios interceptor on API calls) and in memory. The only cookie the dashboard sets from script is a `signed_in=1` marker that holds no credential: the edge middleware reads it to choose between a page and the sign-in redirect and the API checks the real token on every request. The refresh token is an httpOnly cookie that only the API reads. Script that runs on a dashboard page can still read `localStorage`, which is why the dashboard pages carry a nonce-based Content-Security-Policy. Where the site and the dashboard share one address (self-hosting and previews) the public pages share that storage and keep `'unsafe-inline'`, so use two addresses in production.

**Rate limiting in Docker:** slowapi uses the client IP for rate limiting. If running behind a reverse proxy, set `FORWARDED_ALLOW_IPS` or configure `X-Forwarded-For` trust to avoid all requests appearing as the proxy IP.

**CORS:** `allowed_origins` is set in `app/config.py` via the `ALLOWED_ORIGINS` environment variable. The default allows `http://localhost:3000` for local development only. Set this to the production frontend URL before deploying.
